# 委任テンプレート

指示書・依頼書は scratchpad にファイルとして保存し、各 adapter の canonical command から `"$(cat <ファイル>)"` で渡す。テンプレートは次の3種類だけ。

## 1. 実装指示書

書き込み委任(Codex / 例外的に Grok・Antigravity)に使う。設計判断は Claude Code が済ませた状態で渡し、委任先に選ばせない。大きな機能は1回で渡さず、レビュー可能な単位に分割して順に委任する。

```markdown
# 実装指示書: <タスク名>

## 目的と背景
(1〜2行)

## 対象
- <ファイルパス>(<関数名・行範囲>)
(委任先はリポジトリを直接読めるので、コード全文の貼り付けは不要)

## 変更するユーザー可視挙動
- (設計時に棚卸しした現行挙動のうち「この委任で意図して変えるもの」を列挙。
   ここに書いていない可視挙動の変更は起きない、がレビュー基準になる)

## 期待する挙動・仕様
- 

## スコープ外(やらないこと)
- 

## 既知の状態(ベースライン)
- (委任前に実測した typecheck / lint / テストの結果。
   既存の失敗があれば「これは修正しない」と明記する)

## 完了条件
- (例: `tsc --noEmit` が通る。委任前より失敗が増えていない)

---
確認や質問は不要です。ファイルへの反映まで自主的に完了させてください。コミット・プッシュは行わないでください。
検証を妨げるスコープ外の問題を見つけた場合は、修正せず最終レポートに列挙するに留めてください。特に、定数・仕様値・生成条件など挙動を変える修正は理由を問わず禁止です。
最終レポートには、変更した全ファイルを「パス + 変更理由1行」の形式で漏れなく列挙してください。
```

記入時の注意:

- **対象機能に複数系統の実装(ストアのドライバ別・環境別分岐・モック実装など)がある場合**は、ファイルを限定列挙で閉じず「全系統を揃えること。系統は全域grepで洗い出すこと」と明記する(列挙漏れの事故例が `lessons.md` にある)
- ベースラインに失敗がある場合、「全テストパス」を完了条件にしてはならない(スコープ外修正を誘発する)
- ブラウザ・実DB・課金APIを伴う実行時検証がある場合、**「実施はこちらで行うので、動くはずの状態にしておくこと」と明記**する(委任先が課金APIや実ブラウザで検証を試みてコストを浪費するのを防ぐ。検証の設計と実施は司令塔の責務)
- 障害修正で証拠が不完全な場合は「事実」と「仮説」を分けて書く(`SKILL.md`「ベースライン規約」3)

## 2. 詳細設計ドラフト依頼書

複数ファイル横断・設計の選択肢が割れる・リスクが読めない機能で、実装委任の前に read-only 相談として使う(単純な修正で使うと委任の管理コストが実装コストを上回るので使わない)。委任してよいのは「詳細設計ドラフト・代替案・リスク洗い出し・実装分割案」まで。

委任先は `SKILL.md`「役割分担」に従う: コード密着の設計は Codex read-only、大規模読解・技術ドキュメント調査を伴う設計は Antigravity、外部事情・速報が絡む場合は Grok。

```markdown
# 詳細設計ドラフト依頼: <機能名>

## 目的と制約
(1〜2行。譲れない条件、コスト・運用の前提)

## 現行のユーザー可視挙動(棚卸し済み)
- (何が表示され、何が隠れ、何がエラーになるか。Claude Code が事前に列挙する)

## 検討してほしい代替案の軸
- (例: 同期 vs 非同期、テーブル追加 vs カラム追加)

## 出力形式
- 推奨案とその根拠
- 代替案(1〜2)とトレードオフ
- リスクと前提が崩れる条件
- レビュー可能な単位への実装分割案

---
確認や質問は不要です。リポジトリの読み取り・検索・コード確認は積極的に行ってください(禁止するのはファイルの作成・変更だけです)。具体的な設計案・提案まで自主的に出力してください。
```

ドラフトの扱い(受領後に Claude Code が行う):

- Web調査を含むドラフトには `SKILL.md`「Web調査結果の原典確認」を適用する
- ユーザー可視挙動が変わる選択肢は製品判断としてユーザーに確認する
- 採用部分だけを「実装指示書」テンプレートへ昇格させ、不採用案は理由1行で記録に残す
- 委任ログには `kind:"相談"` で記録する(task 要約に「詳細設計ドラフト」と書けば集計で区別できる)

## 3. 独立レビュー依頼書

高リスク変更で必須(`SKILL.md`「リスク判定」)。実装者とは別モデルに read-only で依頼する。担当は Antigravity / Claude サブエージェント / Grok の持ち回り(選び方と高リスク時の例外は `SKILL.md`「独立レビュー」)。

**ブラインド規律**: 実装者の成功宣言・設計正当化・「既知の問題なし」評価は渡さない。渡すのは客観物(指示書・diff・変更ファイル一覧・検証結果)だけ。レビュー結果を受け取ってから実装者のレポートと照合する。

```markdown
# 独立レビュー依頼: <タスク名>

あなたはこの変更の実装者とは別のレビュー担当です。以下の材料だけで独立に判断してください。

## 実装指示書(確定版)
(全文を貼るか、パスを指定)

## 変更ファイル一覧
(git status 由来の客観リスト)

## diff
(git diff の全文、またはパッチファイルのパス)

## ベースライン(委任前の検証結果)
- 

## 変更後の検証結果
- 

## レビュー観点
- 指示書からの仕様逸脱(指示書に書かれていないユーザー可視挙動の変更を含む)
- 副作用・退行リスク
- スコープ外変更の混入
- テスト不足
- (高リスク領域が絡む場合: 認証・権限・課金・顧客データ・DB移行・セキュリティ・不可逆性の具体的懸念)

## 出力形式
指摘ごとに: 重大度(高/中/低)/ 該当ファイル・行 / 問題の説明 / 推奨処置。
問題がなければ「指摘なし」とし、何をどう確認したかを書いてください。

---
確認や質問は不要です。具体的な指摘まで自主的に出力してください。ファイルの作成・変更・削除とコマンド実行は禁止です(検証結果は上に貼ってあるものを使ってください)。
```
