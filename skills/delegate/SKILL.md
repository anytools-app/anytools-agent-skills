# 外部AI委任とモデルルーティング(中核規約)

Claude Code が司令塔として設計・指示書・レビュー・採否・コミットを握ったまま、実装・調査・独立レビューを外部AI CLI(Codex / Grok / Antigravity)と Claude サブエージェントへ委任するための中核規約。モデル名・CLIフラグ・認証手順・バージョン固有の罠はこのファイルには置かず、adapter と lessons に置く。

## 参照ファイル

通常はこの `SKILL.md` だけを読む。委任先を決めた後、使用する CLI の adapter だけを追加で読む。

- Codex を使う: `adapters/codex.md`
- Grok を使う: `adapters/grok.md`
- Antigravity を使う: `adapters/antigravity.md`
- 指示書・依頼書を作る: `templates.md` の該当セクション
- CLI 失敗・過去事故の確認、ログの集計・見直し、自動化の昇格条件: `lessons.md` の該当セクション

使わない CLI の adapter や、通常時の `lessons.md` 全体は読まない。

## 役割分担(大前提)

- **Claude Code(あなた)が最終責任者**: 設計、実装指示書の作成、成果物レビュー、採否判断を担当し、**コミット・プッシュは常に Claude Code が行う**
- 委任先の分担は「現在のデフォルト」であって絶対的な責務ではない。見直すのは、委任ログで `routing_verdict:"委任先ミス"` が同じ能力不足を理由に偏った場合だけ(`lessons.md`「ログの見直しと昇格条件」)

| タスク | デフォルト委任先 |
|---|---|
| 通常実装 | Codex |
| Web/X・速報系の調査、コミュニティ色の強い第三意見 | Grok |
| 大規模読解、Google検索付きドキュメント調査、独立レビュー、技術文脈の第三意見 | Antigravity(Gemini) |
| 設計前の安価なコードリーディング・広い探索 | Claude サブエージェント |
| 最終設計、製品判断、採否、コミット | Claude Code(委任しない) |

- 設計判断を委任先に丸投げしない。詳細設計の委任は「ドラフト」まで(下記「タスク種別」)
- Codex / Grok / Antigravity の成果物・指摘は鵜呑みにせず、Claude Code が妥当性を判断してから反映する

## 窓口(司令塔モデル)の固定

ユーザーが話しかける相手は常にメインセッションの Claude Code(窓口=司令塔)であり、窓口の上に別の司令塔を置かない。要求解釈、製品判断の確認、委任先選定、成果物の採否、最終報告まで窓口が一貫して担当し、委任先の出力は助言または成果物であって最終判断ではない。

- 窓口モデルの選択は `~/.claude/settings.json` の `model` に属し、`"best"`(Fable にアクセスがあれば Fable、なければ最新 Opus に解決される公式エイリアス)での固定を推奨する。タスクごとに司令塔モデルを選び直さない — 実装トークンは委任先へ流れ、軽いタスクは直接処理で消費が小さいため、司令塔を最上位に固定してもコスト影響は限定的で、司令塔のレビュー品質が全体の品質上限になる
- このスキルと委任フローは、メインセッションのモデル・effort を**変更しない**。この SKILL.md の frontmatter に `model` / `effort` を書かない(スキル起動でセッション設定が上書きされる)。手順として `/model` 切替や `opusplan` への切替も行わない
- タスクに応じて変えてよいのは委任先の設定だけ: Claude サブエージェントの model、Codex の model / reasoning effort、Grok の effort、Antigravity の model(いずれも各 adapter のモデル表が正)
- 窓口の能力不足を感じた場合もメインモデルを切り替えず、read-only の詳細設計・技術レビュー委任(「タスク種別」)→ 高リスクなら独立レビュー追加 → 残る製品判断はユーザー確認、の順でエスカレーションする

## 委任可否ゲート(最初に判定)

次の条件を**すべて**満たす場合は、Claude Code が直接処理してよい。

- 変更結果が一意で、設計判断を伴わない
- ユーザー可視挙動・仕様値・生成条件を変えない
- 認証・権限・課金・顧客データ・DB移行・セキュリティに触れない
- 広いコードリーディングを必要としない
- 指示書作成・委任・レビューのコストが実装コストを明らかに上回る

1つでも満たさない場合は、調査・詳細設計・実装・独立レビューのいずれかに委任する。挙動・仕様・生成条件に触る変更は、行数が少なくても委任+レビューの対象にする。

## タスク種別

- **調査**: コードリーディング、原因候補の洗い出し、Web調査
- **詳細設計**: 詳細設計ドラフト、代替案、リスク洗い出し、実装分割案。あくまでドラフトであり、**最終設計への昇格、製品判断、スコープ確定、実装順序、完了条件は Claude Code が決める**。委任先の設計案をそのまま実装指示書にしない
- **実装**: ファイル変更を伴う作業
- **独立レビュー**: 実装者とは別モデルによる仕様逸脱・副作用・テスト不足の確認(高リスクで必須。下記「独立レビュー」)

## リスク判定(3段階)

「複数ファイルだから高リスク」ではない。影響の意味で判定する。

| リスク | 対象 | 必須レビュー |
|---|---|---|
| 低 | 機械的変更、内部的で結果が一意な変更 | 対象 diff、対象の検証 |
| 標準 | 通常機能、複数ファイル、ユーザー可視挙動の変更 | 全 diff、ベースライン比較 |
| 高 | 認証、権限、課金、生成品質・コスト、顧客データ、DB移行、セキュリティ、不可逆変更 | 全 diff、ベースライン比較、独立レビュー、rollback 確認、必要な製品判断 |

## 製品判断と技術判断

技術判断は Claude Code が決めてよい。製品判断は委任前にユーザーへ影響と選択肢を1行で確認する。

ユーザー確認が必要(製品判断):

- 成功・失敗の意味が変わる
- 生成物の品質・見た目・選定条件が変わる
- 表示・非表示の条件が変わる
- 課金額・APIコスト・実行回数が変わる
- データ保持・削除・移行の条件が変わる
- 権限・公開範囲が変わる
- 後方互換性が壊れる
- 既存仕様から一意に決まらない文言・UX選択

Claude Code が決めてよい(技術判断):

- 明白な誤字
- 内部ログ文言
- 既に承認済みの仕様へ合わせる修正
- 外部挙動を変えない内部実装
- ユーザー要求から一意に決まる変更

## モデルルーティング

- ティアの原則: 機械的な作業は低ティア、標準実装は中ティア、難所(複雑なリファクタ・原因不明の障害・高い退行リスク)だけ高ティア。**迷ったら中ティア**。effort は低めから試し、委任ログで評価してから上げる
- 高ティアを頻繁に使う状態は、モデル不足ではなくタスク分割または指示書の不足を疑う
- 具体的なモデル名・effort・フラグは各 adapter のモデル表に従う(このファイルには置かない)
- **Claude サブエージェント**: 設計前のコードリーディング・広い探索は Agent ツールの読み取り専用サブエージェント(機械的な探索は `model: haiku`、判断を伴う調査は `sonnet`)に委任し、ファイル全文をメイン会話に持ち込まない。「何を調べ、何を返すか」を明示し、返答はパス・行番号・結論に絞らせる。設計判断そのものはサブエージェントにも委任先にも丸投げしない

## 基本フロー

1. 委任可否ゲートを判定する → 直接処理 or 委任
2. タスク種別とリスクを判定する。**既存フローを変更する設計では、現行のユーザー可視挙動(何が表示され、何が隠れ、何がエラーになるか)を先に列挙し、「意図して変えるもの」を特定する。列挙できないなら調査に戻る**
3. 製品判断が含まれるならユーザーに確認する
4. 委任先を決め(「役割分担」の表)、その adapter だけを読む
5. ベースラインを計測する(下記)
6. 指示書を書く(`templates.md`)。大きな機能は1回で渡さず、レビュー可能な単位に分割して順に委任する
7. adapter の canonical command で実行する。生成・実行は原則 `bin/delegate-run` を使う(必須フラグ・事前チェック・ログ隔離・session ID 控え・runs.jsonl 記録を自動化。`--dry-run` で実行前にコマンドを確認できる。canonical command の正は引き続き各 adapter)
8. 成果物をレビューする(下記)。高リスクは独立レビューを挟む
9. 修正は元セッションへの継続指示で、同一原因につき最大2回(下記「修正・再委任の上限」)
10. 合格した変更だけ Claude Code がコミットし、採用・修正・除外した点をユーザーに報告する
11. 委任ログに1行追記する(下記)

## ベースライン規約(委任前に必ず)

1. **検証コマンドを一度実行する**(typecheck / lint / テスト)。既知の失敗があれば指示書に明記し、完了条件を「全部パス」ではなく**「委任前より失敗を増やさない」**にする。怠ると、委任先が「テストを通すため」にスコープ外の既存問題まで修正し、挙動変更が混入する
2. **`git status` でツリーの状態を確認する**。既存の未コミット差分は先にコミットするか stash してから委任する。残す場合は指示書に「触らないこと」と明記し、レビュー時に除外して見る
3. **障害修正の委任は、決定的証拠を得てから**。エラーログの原文・再現手順など動かぬ証拠を先に取る。証拠が取れないまま委任する場合は、指示書で「事実」と「仮説」を明確に区別し、仮説向けの修正は空振りしても害のない最小限に絞る。**「前はできていた」系の報告は、症状発生前のコミットの実コード(`git show <コミット>:<ファイル>`)で当時の挙動を確認し、現行との差分を証拠にする**

## 成果物レビュー(必須)

書き込み委任の成果物をそのまま信用しない。リスク段階の必須レビューを下限として:

1. **変更ファイルのマニフェスト照合** — 委任先レポートの「変更ファイル一覧」と `git status` を突き合わせ、指示書のスコープ外のファイルが混ざっていないか確認する。レポートに一覧がなければ継続指示で提出させる
2. `git diff` を読む(標準リスク以上は全部) — 設計との一致、副作用、無関係な変更の混入をチェック。スコープ外の変更は妥当でも安易に受け入れず「今回のコミットに含めるか」を独立に判断する(必要なら該当ファイルだけ除外してコミット)
3. プロジェクトの検証手段(typecheck / lint / テスト / ビルド)を実行し、**ベースラインと比較する**(新たな失敗がないか)。委任中に外部ツールがツリーへ書き込みスコープ外ファイルで lint が落ちた場合は、委任先には変更ファイル単位の check で代替させ、lint/git 除外の設定追加(数行)は司令塔が直接処置してよい
4. ブラウザ・実DB・課金APIを伴う実行時検証は司令塔が設計・実施する(指示書には「実施はこちらで行う」と明記)。実際に処理を走らせず、状態を直接注入して疑似再現する形を優先する — モック、テストレコード作成用 debug エンドポイント、DB 直接更新が道具(実例は `lessons.md`)
5. 高リスクは独立レビュー(下記)の結果を突き合わせてから採否を決める

## 修正・再委任の上限(retry budget)

- 修正は**元の委任先セッション**への継続指示(resume)で依頼する(コマンドは各 adapter)。修正指示には「何が・どのファイルのどこで・どう間違っているか」と再検証コマンドを明記する
- **同じ原因に対する同一セッションへの修正指示は最大2回**。2回で解消しない場合は、追加 resume を止めて原因を分類する
- **別の委任先へ黙って乗り換えない**。原因分類と Handoff を作った場合に限り、モデル・セッション・委任先を変更してよい

| cause | 処置 |
|---|---|
| `instruction` | 指示書を修正して再委任 |
| `spec_change` | 設計・製品判断へ戻る |
| `model` | 上位モデルまたは別プロバイダを検討 |
| `tooling` | CLI・adapter・実行方法を変更 |
| `environment` | 環境を直してから再実行 |
| `product_decision` | ユーザー判断へ戻る |
| `unknown` | 修正せず証拠取得へ戻る |

乗り換え・引き継ぎ時の Handoff は短い文章で足りる(新しい指示書の冒頭に添える):

```markdown
### Handoff
- 採用済み変更:
- 未解決の問題:
- 確認済み事実:
- 失敗した試行:
- 維持すべき不変条件:
- 禁止する変更:
```

## 委任先の limit と cooldown

委任先 CLI が limit・クォータ切れで使えないと分かったら、その事実を cooldown として記録し、回復見込みまで再試行しない(**「使ってみる→失敗→代替」を毎回繰り返さない**):

- `delegate-run` は limit パターンを含む失敗(exit≠0)を検知すると**自動で 1h の cooldown を記録する**。exit 0 でパターンだけ見えた場合は警告に留まるので、実際に limit なら `delegate-run --set-cooldown <cli> <期間>` で手動記録する(リセット周期が分かっているならその長さで)
- **cooldown 中の CLI への委任は delegate-run が実行前に拒否する**。拒否されたら待たずに下の表で代替へルーティングする。確認は `--cooldowns`、解除は `--clear-cooldown <cli>`、解除済みと分かっている場合のみ `--force` で強行し、通ったら `--clear-cooldown` する
- 状態はログディレクトリの `cooldowns.json` に永続化され、セッション・プロジェクトを跨いで共有される

| limit 中の CLI | 代替 |
|---|---|
| Antigravity(大規模読解・独立レビュー) | Grok `--model grok-4.5`(500k context。`adapters/grok.md`) |
| Grok(Web/X 調査) | Antigravity(Google Search 併用。`adapters/antigravity.md`) |
| Codex(実装) | 高リスクでなければ Grok workspace 実装(`adapters/grok.md`)。または委任を分割して Claude Code が直接処理、急がなければ回復を待つ |

- 代替先で実行した委任も通常どおり委任ログに記録する(`note` に「本来は X だが cooldown のため代替」と書けば、後の見直しで cooldown 起因の `routing_verdict` を除外できる)

## 独立レビュー(高リスクで必須・ブラインド)

実装者の自己評価に引っ張られないよう、レビュー担当(実装者とは別モデル。デフォルトは Antigravity の Gemini 系)には客観物だけを渡す。依頼書は `templates.md`「独立レビュー依頼書」。

先に渡すもの:

- 確定済みの実装指示書
- `git diff`
- 変更ファイル一覧
- ベースライン結果
- 変更後の検証結果

先に渡さないもの:

- 実装者の成功宣言
- 実装者自身の設計正当化
- 実装者の「既知の問題なし」という評価

独立レビュー結果を取った後に、実装者のレポートと照合する。変更ファイル一覧は客観的マニフェストなので隠さない — 隠すのは主観評価だけ。

## 並列委任時の worktree 分離

同じ working tree で**複数の書き込み委任を同時に走らせない**(どれがどのエージェントの変更か判別できなくなり、マニフェスト照合と diff レビューが崩壊する)。比較実装や独立タスクの並行委任で書き込みが同時に必要な場合:

- Claude Code が事前に `git worktree add` でエージェントごとの worktree を切り、各 CLI を worktree に向ける(向け方は各 adapter)
- 採用する差分は Claude Code がメイン worktree へ patch / cherry-pick で取り込む。worktree 側でコミットさせない(コミットは常にメイン側で Claude Code が行う)
- worktree 削除前に `git status` と `git diff` で未回収の変更・未追跡ファイルがないか確認する
- read-only の相談は原則同一ツリーで並走してよい(Codex / Grok は OS レベルで書き込みが制限される)。**例外: Antigravity は read-only 保証がない**ため、`adapters/antigravity.md` の「worktree に隔離する条件」に従う

## 秘密情報・外部送信ルール

外部 AI CLI への委任は、読ませたコード・ログの外部送信を伴う。委任前に確認する:

- `.env`・秘密鍵・認証トークン・DB接続文字列・顧客データ・本番ログは**原則読ませない。指示書にも貼らない**
- 文脈上どうしても必要な場合は、ファイルを読ませるのではなく、Claude Code が値をマスクした最小限の抜粋だけを指示書に含める。CLI 側の環境変数制限設定(例: Codex の `shell_environment_policy`)は防波堤にすぎず、「読ませない・貼らない」が一次防御
- 委任先の作業ログ(scratchpad のログファイル)には秘密が混ざりうる前提で扱い、リポジトリにコミットしない

## Web調査結果の原典確認

Grok / Antigravity の Web 調査結果は、司令塔が原典を確認するまで**「仮説」として扱い、そのまま設計事実・実装指示書に昇格させない**(検索結果の要約が設計事実に化けるのが、Web調査担当を置く最大のリスク):

- 実装判断に使う主張は、Claude Code が一次情報(公式 docs / changelog / release note / issue / PR)を開いて確認し、原典 URL を記録に残す
- 委任先の要約に URL がない、または引用先を開いたら主張を支持していない場合は採用しない
- バージョン依存の仕様は、対象プロジェクトの lockfile / CLI・SDK の実バージョンと照合してから指示書に入れる(鵜呑みで全委任コマンドが壊れかけた実例が `lessons.md` にある)
- 調査結果を指示書に含める場合は「確認済み事実」と「仮説」を分けて書く(「ベースライン規約」3 と同じ規律)

## 委任ログ

委任(実装・相談・レビューとも)の完了時に、ログディレクトリの `delegation-log.jsonl` に1行追記する(規約=スキルと運用データ=ログは分けて置く)。ログディレクトリは**スキル直下の `.env` の `DELEGATE_LOG_DIR`**(環境変数があればそちらが優先。どちらも未設定なら `~/.claude/logs/delegate`)。**レビューまで到達しなかった失敗(認証エラー・timeout・権限詰まり・途中打ち切り)も必ず記録する** — 運用摩擦こそルーティング改善の主データになる。手書き JSON は task/note 内の引用符で壊れるため、必ず次の `jq -cn` で追記する:

```bash
SKILL_DIR="<このスキルの Base directory(スキル起動時に表示されるパス)>"
set -a; [ -f "$SKILL_DIR/.env" ] && . "$SKILL_DIR/.env"; set +a
LOG_DIR="${DELEGATE_LOG_DIR:-$HOME/.claude/logs/delegate}"
mkdir -p "$LOG_DIR"
jq -cn \
  --arg date "$(date +%F)" \
  --arg repo "<リポジトリ名>" \
  --arg task "<1行要約>" \
  --arg kind "<実装|相談|レビュー>" \
  --arg cli "<codex|grok|agy|claude-agent>" \
  --arg model "<モデル>" \
  --arg effort "<effort/なし>" \
  --arg outcome "<採用|一部採用|破棄|未完了|失敗>" \
  --arg validation "<pass|no_new_failures|fail|not_run>" \
  --arg delegation_verdict "<必要|委任不要>" \
  --arg routing_verdict "<適正|過剰|過小|委任先ミス>" \
  --arg cause "<model|instruction|spec_change|environment|tooling|product_decision|unknown>" \
  --arg note "<判定理由1行>" \
  --arg run_id "<delegate-run の run_id/なし>" \
  --argjson resumes <回数> \
  --argjson scope_violation <true|false> \
  '{date:$date,repo:$repo,task:$task,kind:$kind,cli:$cli,model:$model,effort:$effort,outcome:$outcome,validation:$validation,resumes:$resumes,scope_violation:$scope_violation,delegation_verdict:$delegation_verdict,routing_verdict:$routing_verdict,cause:$cause,note:$note,run_id:$run_id}' \
  >> "$LOG_DIR/delegation-log.jsonl"
```

- **判定は2軸に分ける**: `delegation_verdict` は「そもそも委任すべきだったか」(委任可否ゲートで直接処理すべきだったなら `委任不要`)、`routing_verdict` は「選んだ CLI/モデル/effort が適切だったか」(`過剰`=下位ティアで足りた / `過小`=能力不足 / `委任先ミス`=別CLIが適切)。両方同時に悪いことがあるので独立に記録する
- `outcome` は成果物の最終処遇、`validation` は**委任成果物をレビューした時点**の検証結果(ベースラインに既存失敗がある場合、新規失敗ゼロなら `no_new_failures`)。Claude Code の軽微修正後に結果が変わった場合は最終結果を入れつつ、`note` に「軽微修正後pass」等と明記する(委任先が一発で通したように見せない)
- `未完了` は**ユーザー都合・仕様変更・作業中断など、委任先や環境の失敗ではない理由**に限る。CLIエラー・認証エラー・timeout・権限詰まりは `失敗`(+ `validation:"not_run"`、`cause` に `tooling|environment|unknown` 等)
- **手戻りの起因は `cause` で構造化する**(値と処置は「修正・再委任の上限」の表)。resume が多くても `cause` が `instruction` や `spec_change` ならモデル評価に使わない。`routing_verdict:"過小"` の根拠にできるのは `cause:"model"`(指示の誤解・雑な実装・虚偽の完了報告)だけ。**独立レビューの指摘を反映するための resume は正常工程であり、それ自体は cause に数えない**(指摘の根因が指示書の誤り・欠落である場合のみ `instruction`。76件見直しでレビュー反映 resume が `instruction` に混ざり指示書品質のシグナルが濁った実例あり)
- `cli:"claude-agent"` は設計前の本格的なコードリーディング委任(Explore 等に数分規模で振ったもの)を対象とし、軽い単発検索は記録しない
- 相談の判定材料は回答の質(原典確認で嘘が見つかったか、提案が採用に耐えたか)
- 追記時に `wc -l` で件数を確認し、**10の倍数でユーザーに集計・見直しを提案する**(「委任ログを見直して」でも随時)。集計コマンド、ルーティング表・モデル表の更新条件、自動化の昇格条件は `lessons.md`「ログの見直しと昇格条件」
- このログはローカル専用(リポジトリにコミットしない)。task/note に秘密情報を書かない
